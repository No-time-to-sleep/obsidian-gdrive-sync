# Алгоритм синхронизации

Документ описывает, как принимаются решения о синхронизации. Реализуется на этапе 04 (см. `PLAN.md`). Общая архитектура — в `ARCHITECTURE.md`.

## 1. Основные понятия

- **База (base)** — хеш содержимого файла на момент последней успешной синхронизации, сохранённый в state.
- **Локальное изменение** — хеш локального файла не совпадает с base (или файл появился, если base нет).
- **Remote-изменение** — `md5Checksum` файла в Drive не совпадает с base (или файл появился).
- **Отсутствие** — файла нет на локальной стороне или он не виден в успешном полном remote-скане.
- **Конфликт** — обе стороны изменились, и хеши различаются.

## 2. Порядок синхронизации (pipeline)

1. **Lock.** Если синк уже идёт — новый запуск игнорируется.
2. **Auth guard.** Проверить токен; при необходимости refresh; при `invalid_grant` — остановка со статусом «переподключиться».
3. **Remote scan.** Полный листинг метаданных всех видимых приложению файлов и папок. Скан считается успешным только если все страницы получены без ошибок.
4. **Local scan.** Обход vault, фильтрация игноров, сбор `path → {mtime, size}`. Хеши считаются лениво.
5. **Build plan.** Для каждого пути из объединения (state, local, remote) вычисляется решение (см. таблицу ниже). Удаления включаются в план только при успешном remote-скане.
6. **Sort.** Порядок операций: сначала папки (создание), затем downloads, затем uploads, затем trash/conflict. Стабильный порядок по пути.
7. **Execute.** Операции выполняются с ограниченным параллелизмом; результат каждой фиксируется в state сразу после успеха.
8. **Persist.** State сохраняется (debounced).
9. **Report.** Итог: `up`, `down`, `conflicts`, `trashed`, `errors`; статус-бар и запись в лог.

Перезапуск после падения безопасен: state отражает только реально выполненные операции, повторный скан сгенерирует эквивалентный план.

## 3. Таблица решений

Обозначения: `= base` — совпадает с базой; `≠ base` — изменён; `нет` — отсутствует; `новый` — есть, но base нет.

| # | Base | Локально | Remote | Действие |
| --- | --- | --- | --- | --- |
| 1 | есть | = base | = base | Ничего |
| 2 | есть | ≠ base | = base | **Upload** локальной версии |
| 3 | есть | = base | ≠ base | **Download** remote-версии |
| 4 | есть | ≠ base | ≠ base, хеши равны | Обновить base (adopt) |
| 5 | есть | ≠ base | ≠ base, хеши разные | **Conflict**: локальная остаётся, remote сохраняется как conflict copy, локальная загружается |
| 6 | есть | нет | = base | **Trash remote** (локальное удаление распространяется) |
| 7 | есть | = base | нет | **Trash local** (удаление пришло из remote) |
| 8 | есть | нет | нет | Убрать из state (оба удалили) |
| 9 | есть | нет | ≠ base | **Restore local** из remote (не терять remote-правки) |
| 10 | есть | ≠ base | нет | **Upload** заново (не терять локальные правки) |
| 11 | нет | новый | нет | **Upload** (новый файл) |
| 12 | нет | нет | новый | **Download** |
| 13 | нет | новый | новый, хеши равны | Добавить в state (adopt) |
| 14 | нет | новый | новый, хеши разные | **Conflict**: локальная каноническая, remote — conflict copy |
| 15 | есть, папка | нет | есть (после успешного скана) | Удалить папочную запись; файлы обрабатывает общий проход |

Правила-инварианты:

- Ни одно решение не выполняет permanent delete.
- Решения 6 и 7 выполняются только в рамках успешного полного скана.
- Если скачивание/загрузка упала, state не обновляется, и в следующем проходе будет повторная попытка.

## 4. Конфликты

- Имя копии: `<имя> (conflict YYYY-MM-DD HHMM, <device>).<ext>`; `device` — короткое имя устройства (настраиваемое, по умолчанию из `Platform`), санитизированное от запрещённых символов.
- Если имя занято, добавляется ` 2`, ` 3` и т.д.
- Содержимое копии — версия из remote на момент конфликта; локальная версия остаётся канонической и загружается.
- Conflict copy синхронизируется как обычный новый файл (без специального статуса).
- Уведомление в UI: путь и количество конфликтов; лог для разбора.
- Автоматический merge — не в MVP. Для markdown возможен отдельный режим в будущем (по мотивам Google Drive Merge Sync, см. `COMPARISON.md`).

## 5. Удаления

- Локальное удаление файла, который не менялся на remote → `files.update trashed=true`.
- Удаление файла на remote (или перемещение за пределы видимости `drive.file`) → локальный файл отправляется в `.trash` Obsidian, а не удаляется навсегда.
- Если один из пользовательских File Managers удаляет файл локально без Obsidian API (например, через файловую систему), событие может не прийти; периодический скан и отсутствие файла в успешном скане дадут то же решение (6).
- Папки: удаление папки обрабатывается как удаление файлов внутри + удаление папки; при `drive.file` вложенные файлы видны, поэтому операция безопасна.

## 6. Переименования и перемещения

- В штатном режиме плагин получает событие `rename` с `oldPath` и `newPath`:
  - помечаем файл как «ожидает переименования»;
  - обновляем `name`/`parents` в Drive, сохраняя `fileId`;
  - в state переносим запись на новый путь (для папки — все вложенные пути).
- Если событие было пропущено (плагин выключен, Obsidian закрыт):
  - скан видит «нет на старом пути» + «новый на новом пути»;
  - сначала пытаемся распознать переименование по совпадению хеша/размера среди отсутствующих локальных и новых remote-записей;
  - если однозначной пары нет — старое удаляется в trash, новый файл загружается как новый. Это может создать новую Drive-запись, но не теряет данные.
- Смена регистра и Unicode-нормализация имён (NFD/NFC на macOS/iOS) — частный случай переименования; сравнение путей ведётся в нормализованной форме, отдельные тайм-кейсы фиксируются на этапе тестирования.

## 7. Первичный синк (нет state)

Три режима в настройках:

1. **Local → Drive** (по умолчанию для нового пустого remote): загрузить весь vault.
2. **Drive → Local** (новое устройство): скачать всё, что видно, ничего не удаляя локально до явного подтверждения.
3. **Safe merge** (по умолчанию при непустых обеих сторонах): правило 11–14; конфликты сохраняются копиями; удаления не выполняются.

Перед первичным сканом UI показывает предварительную статистику: сколько файлов локально/на remote, сколько конфликтов ожидается, и требует подтверждения.

## 8. Папки

- Папки создаются до файлов.
- Источник путей для stage — локальные относительные пути; remote-папки сопоставляются по иерархии и имени.
- При конфликте имён папок (две папки с одним именем и родителем) выбирается папка с `appProperties.vaultId`, иначе выводится предупреждение и синк останавливается до ручного разрешения.

## 9. Игноры и специальные файлы

- По умолчанию: `.obsidian/workspace*.json`, `.obsidian/cache/**`, `.trash/**`, `node_modules/**`, `.git/**`, `data.json` плагина, файлы > лимита.
- Google-native файлы (`application/vnd.google-apps.*`) игнорируются: они не могут быть синхронизированы как обычные.
- Ярлыки Drive (`application/vnd.google-apps.shortcut`) — не поддержаны в MVP.

## 10. Идемпотентность и crash safety

- State меняется только после успешного завершения операции над файлом.
- Каждая операция формируется из текущего state + результатов сканов, поэтому повторный запуск после crash/stale state приводит к корректному (возможно, повторному) действию.
- Загрузка в Drive выполняется через `files.create`/`files.update` по `fileId` из state; при отсутствии `fileId` поиск по `appProperties`/пути предотвращает создание дубликата.
- Скачивание: сначала во временный файл в vault, затем `rename` в целевой путь; временные файлы удаляются при старте синка.

## 11. Производительность

- Хеширование — ленивое, только для изменившихся `mtime`/размера.
- Параллелизм операций 4–6, лимит регулируется.
- Полный remote-скан: страницы по 1000, поля минимально необходимые.
- Мобильные лимиты: по умолчанию не трогать файлы > 25 MB, не хешировать их и явно писать в логе «skipped (size)».

## 12. Что считается «полным успешным сканом»

- Все страницы `files.list` получены без ошибок и без превышения retry-лимита.
- Дерево папок от корневой папки плагина построено связно.
- Только при этих условиях разрешены решения 6, 7 и 8 (удаления). Иначе план строится без удалений, а в логе появляется запись `scan incomplete: deletions deferred`.
